## 3. ข้อค้นพบหลัก

1. **chat ×2 ขยายได้เชิงเส้น แต่ ×4 ไม่ขยายต่อ**: baseline 16 → ×2 32 → ×4 16 คน (1.00× ของ baseline) แม้มี 5090 ถึง 4 ใบ (`REPORT.md`)
2. **LLM ไม่ใช่คอขวดที่ ×4**: ทั้ง 4 ใบได้รับงานจริง (telemetry สูงสุด 100%) แต่ **ใช้งานเฉลี่ยเพียง 8–16%** ระหว่างรัน และความยาวคิว chat ที่ 32 คนเกือบเท่า ×2 (28 เทียบ 24) → ข้อจำกัดอยู่ที่ขั้นที่ไม่ได้ขยาย: **rerank 4090 ใบเดียว · embedder TEI บน CPU · retrieval/DB ในสแตกเครื่องเดียว** (`REPORT.md` "Chat ×4 did not scale past ×2") — ⚠️ รายงานระบุว่า *ยังไม่ได้แยกพิสูจน์ว่าขั้นใดใน 3 ขั้นนี้เป็นตัวจำกัดจริง* ข้อสรุปเป็นการอนุมานจาก util + ความยาวคิว ไม่ใช่การวัดแยกรายขั้น
3. **STT ×2 = 0 คนเพราะเครือข่าย ไม่ใช่ GPU**: server ถอดเสียง 0.36–0.52 วิ (คิว 0) แต่ client เห็น 4.5–14 วิ สำหรับไฟล์ WAV 165 KB ผ่าน SSH tunnel ไปเครื่องที่ไอร์แลนด์ (`scale-x2-stt-transport-diagnostic.json`) — ตัวเลือก host ราคาถูกสุดไม่ได้พิจารณาที่ตั้ง/แบนด์วิดท์
4. **TTS แยกจาก rerank ช่วยจริงแต่น้อย**: 0 → 1 คน (p95 10.43 วิ) ที่ 2 คน p95 15.94 วิ · TTS execution concurrency = 1 ต่อ GPU (provider health) · ประโยคละ ~7 วิ (p50) → คนที่สองต้องต่อคิว
5. **เสียงครบวงจรยังคือคอขวดของผลรวม**: voice ×2 = 0 (`MISSING_TTS_SENTENCE` · STT+TTS รายประโยครวมกัน) และ mix ×2 = 1 → เพิ่ม LLM อย่างเดียวไม่ทำให้ mix ถึง 200

## 4. จำนวน GPU สำหรับ 200 คน — ประมาณการเดิมใช้ต่อไม่ได้เต็มที่

ประมาณการเชิงเส้นของ T22 (สูตร `ผู้ใช้ × สัดส่วน × 1.2 ÷ U`; `loadtest/REPORT.md`):

| งาน | ผู้ใช้ที่ต้องรับ | U | GPU | $/ชม. |
|---|---:|---:|---:|---:|
| llm 5090 | 240 (คำนวณ) | 16 | ⌈240/16⌉ = 15 (คำนวณ) | 7.96 (คำนวณ) |
| stt 4090 | 72 (คำนวณ) | 16 | ⌈72/16⌉ = 5 (คำนวณ) | 2.07 (คำนวณ) |
| tts 4090 | 72 (คำนวณ) | 1 (×2, แยก rerank) | ⌈72/1⌉ = 72 (คำนวณ · เงื่อนไข: เฉพาะโหมด tts ล้วน ไม่รวม chat/voice) | ไม่คิด — ไม่สมเหตุสมผลในทางปฏิบัติ |

ข้อจำกัดของตัวเลขนี้ (อ่านก่อนใช้):
- สมมติฐานเชิงเส้นเป็นจริงเฉพาะ chat ถึง ×2 — ผล ×4 (1.00×) **หักล้าง** การนับ "15 ใบ LLM" ว่าจะรับ 200 คน เพราะติดขั้นที่ไม่ได้ขยาย
- TTS ที่ 1 คน/GPU หมายความว่าหากไม่ลดงาน TTS ต่อคนหรือเพิ่ม throughput ต่อ GPU จำนวนที่คำนวณได้สูงเกินจริงจนใช้ตัดสินใจไม่ได้
- **จึงสรุปได้เพียง**: จากการวัดจริง ระบบ GPU ปัจจุบัน (ทุกชุดที่วัด) ยังไม่รองรับ 200 คนในเงื่อนไขหลัก · จำนวน GPU ที่ "ถูกต้อง" สำหรับ 200 คน ยังระบุไม่ได้จากข้อมูลนี้

## 5. ข้อเสนอแบบขยายที่ถูกจุด — **ข้อเสนอ ยังไม่ได้วัด**

ลำดับตามหลักฐานในข้อ 3 (ทั้งหมดเป็นสมมติฐานที่ต้องวัดยืนยัน ไม่มีตัวเลขผลลัพธ์ที่คาดไว้):

1. **ขยายขั้น retrieval ก่อน LLM**: เพิ่ม reranker 4090 เป็นหลายใบ (หรือ batch rerank) · ย้าย embedder จาก CPU ไป GPU/เพิ่มจำนวน replica · ตรวจ DB/trigram ด้วย `EXPLAIN` ใต้โหลด ก่อนเพิ่ม 5090 ใบที่ 3–4 (ผลมี 5090 4 ใบไม่ช่วย)
2. **วัดแยกรายขั้นก่อนจ่ายเงิน**: รัน ×4 chat ซ้ำพร้อมเก็บเวลา embed / retrieve / rerank / LLM ต่อคำขอ (ตอนนี้มีแค่ util และความยาวคิว) เพื่อรู้ว่าขั้นไหนเต็มก่อน
3. **STT**: เลือก host ใกล้ + แบนด์วิดท์สูง (พรอมต์ T23 กำหนด `VAST_MIN_INET_DOWN=2000` แล้ว แต่รายงานระบุว่าตัวเลือก host ไม่ได้พิจารณาที่ตั้ง/แบนด์วิดท์ไปยังเครื่องเรา) หรือเรียกผ่านเส้นทางที่ไม่ตัน tunnel เดียว แล้ววัด STT ×2 ซ้ำ เพราะ GPU ถอดเสียงได้ 0.36–0.52 วิ แล้ว
4. **TTS**: ลดงานต่อคน (จำกัดคำตอบเสียง ≤ 600 ตัวอักษรมีใน chat-worker แล้ว) · ลองหลาย TTS GPU หรือ batch · วัด `tts_execution_concurrency` > 1 ให้ได้หลักฐานอิสระ (ตอนนี้ไม่มี)
