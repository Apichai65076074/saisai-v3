# T23 STT timeout investigation (28 October final round)

Prior evidence: archive-20261028-1226/scale-x2.json has three failed voice transactions at U=2: V02, V05 and V10, each HTTP504 at 30.02–30.06 seconds. Five chat transactions succeeded, p95 5.63s. The web voice route uses a 30,000ms RPC deadline. These facts locate the observed failure at the STT RPC boundary; they do not establish a particular CUDA fault. Prior instances were destroyed, so their live traceback cannot be recovered here.

The adapter admitted four simultaneous requests to a WhisperModel with one default execution worker, using beam5 and multiple fallback temperatures, without VAD. The final round serializes model execution while preserving RabbitMQ prefetch4, fixes CPU threads4, enables VAD, uses beam1 / best_of1 / temperature0 and disables previous-text conditioning. The language fallback to Thai is preserved. These are disclosed decode/concurrency changes; this run cannot be treated as an identical-config hardware-only comparison.

No timeout or load acceptance threshold was increased. The adapter now records queue/decode time, with no audio, transcript or credentials in its timing logs. No output cache is added. Primary upstream definition of these options: https://github.com/SYSTRAN/faster-whisper/blob/master/faster_whisper/transcribe.py . VAD removes non-speech and disabling previous-text conditioning reduces failure-loop risk; exact GPU latency still requires measurement.

Before rental: six CPU/fake-engine adapter tests passed, including lazy decoder serialization with four concurrent calls and no lost responses. Four concurrent calls through the complete mock web→MQ→STT path returned HTTP200 in ~1.5s each. These tests validate contracts and admission behavior, not GPU speed or transcription accuracy.
